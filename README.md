# Job Portal — IDOR in Job Posting Deletion

## Summary

An insecure direct object reference (IDOR) in the Job Portal application allows one authenticated employer to delete job postings belonging to another employer. The job management page at `/jobportal/Employer/ManageJob.php` provides deletion links to `/jobportal/Employer/DeleteJob.php?JobId=<id>`. The deletion handler uses the client-supplied identifier without checking whether the current employer owns the referenced posting.

- **Vulnerability class:** Broken Access Control / IDOR
- **CWE:** CWE-639 — Authorization Bypass Through User-Controlled Key
- **Affected endpoint:** `GET /jobportal/Employer/DeleteJob.php?JobId=<id>`
- **Entry page:** `/jobportal/Employer/ManageJob.php`
- **Test environment:** `http://192.168.56.101/jobportal/`
- **Version:** Not established; this report concerns the tested local installation.
- **CVE:** Not assigned.

## Preconditions

Use an authorized test installation, two separate employer accounts (A and B), and a disposable job posting owned by B. This test permanently deletes the selected posting; record its original data or back up the test database first.

## Steps to reproduce

1. Sign in as employer B and create a disposable job posting.
2. Open **Manage Job** and record that posting's `JobId` from its Delete link. Capture evidence showing that it belongs to B.
3. Sign in as employer A using a separate browser profile or replace the session cookie in Burp Repeater with A's cookie.
4. Open **Manage Job** as A and intercept a request generated by a Delete link. Do not forward a deletion of a valuable posting.
5. In Repeater, replace only the `JobId` value with the identifier of B's disposable posting. Keep A's session cookie.
6. Send the request below.
7. Reload B's job listing or check the database. Verify that B's posting has disappeared, while A performed the request.

## Proof-of-concept request

```http
GET /jobportal/Employer/DeleteJob.php?JobId=<EMPLOYER_B_JOB_ID> HTTP/1.1
Host: 192.168.56.101
Cookie: PHPSESSID=<EMPLOYER_A_SESSION_ID>
Connection: close

```

The placeholders must be replaced with the ID of the disposable posting owned by B and the session of employer A. Knowing an object's identifier must not confer permission to delete it.

Equivalent command (replace the placeholders first):

```sh
curl -i --cookie 'PHPSESSID=<EMPLOYER_A_SESSION_ID>' \
  'http://192.168.56.101/jobportal/Employer/DeleteJob.php?JobId=<EMPLOYER_B_JOB_ID>'
```

## Expected result

The server rejects employer A's attempt to delete B's posting, and the posting remains unchanged. Authorization must be checked before executing the DELETE query.

## Observed response and verification

The supplied Burp capture shows a request to `DeleteJob.php?JobId=9` and an HTTP 200 response containing:

```html
<script type="text/javascript">
alert("Job Deleted Succesfully");
window.location='ManageJob.php';
</script>
```

The response alone is not proof that a row was deleted: the handler may display success without checking affected rows. Complete the evidence with a before/after view or database check linking the deleted JobId to employer B and the request session to employer A.

The supplied screenshots show two employer contexts: Wipro Infotech and Solusoft Pvt Limite. The second employer's supplied view contains JobId 12, whereas the Burp request targets JobId 9. These images provide context, but do not independently establish ownership and deletion of JobId 9. Do not claim that they do.

## Root cause

In the reviewed source, `Employer/DeleteJob.php` reads `$_GET['JobId']` and deletes a row using only that identifier:

```php
$Id = $_GET['JobId'];
$sql = "delete from Job_Master where JobId='".$Id."'";
mysqli_query($con, $sql);
```

There is no session/role check or ownership condition in this handler. Table capitalization may differ in the compatibility-patched copy. Direct SQL interpolation is also a separate SQL injection issue; this IDOR reproduction does not require SQL injection.

## Impact

An employer can delete another employer's postings by supplying their identifiers. This compromises data integrity and makes the affected postings unavailable to applicants. This finding does not demonstrate remote code execution or full server compromise.

## Remediation

- Require an authenticated Employer role in the deletion handler.
- Bind each posting to an immutable employer ID, rather than a company display name.
- Perform a parameterized DELETE constrained by both JobId and the employer ID from the authenticated session.
- Use POST with a validated CSRF token for deletion.
- Check affected rows and return an appropriate result.
- Verify that A cannot delete B's posting and that anonymous requests cannot delete any posting.
